# CAVE Infrastructure Docker

A Docker deployment wrapper for the [CAVE Infrastructure](https://gitlab.opencode.de/BSI-Bund/cave/cave-infrastructure-docker) project by BSI-Bund.

This repository provides an easy way to build and run CAVE Infrastructure in Docker containers, including all necessary dependencies (Python, OpenTofu, OpenStack CLI, WireGuard).

## Prerequisites

- Docker and Docker Compose installed
- OpenStack credentials (RC file or environment variables)
- SSH key for deployment
- (Optional) GitHub Container Registry access for pushing images

## Where the scripts run

There are two kinds of scripts. Keep them apart:

| Runs | Scripts | How |
|---|---|---|
| **In the container** | `init-flavors.sh`, `upload-windows-image.sh`, `pre-build-images.sh`, `build-images.sh`, `deploy-wrapper.sh`, `exterminate-wrapper.sh` | `docker compose run --rm cave /cave/<script>`, or pick them from the menu that opens by default (`docker compose run --rm cave`) |
| **On the OpenStack host** (as root, from a checkout of this repo) | `scripts/host-init.sh`, `scripts/ovmf/*`, `scripts/fix_ovn_metadata.sh` | `sudo ./scripts/<script>` |

The host scripts change the OpenStack host itself (NAT, users, firmware, snap patches), so they are neither in the menu nor in the container image. They are only needed for a self-hosted OpenStack, never for a managed one. Everything else talks to OpenStack over its API from the container.

## Setup

### 1. OpenStack
You will need a running OpenStack environment. If you need to set one up, MicroStack (Canonical OpenStack) is a good starting point: [Canonical OpenStack Documentation](https://canonical-openstack.readthedocs-hosted.com/en/latest/)

### 2. Configuration
Clone this repository and create the configuration files:

```bash
git clone https://github.com/FelixHertweck/cave-infrastructure-docker.git
cd cave-infrastructure-docker

# Create your .env file
cp .env.sample .env

# (Optional) Copy your OpenStack RC file if you use one
cp .openrc.sample .openrc
```

Edit the `.env` file to set your credentials, lab prefix, SSH key name, and network configurations. Place **both** the private and public key in the `./ssh-keys/` directory:

```
ssh-keys/
├── id_ed25519        # private key
└── id_ed25519.pub    # public key  ← required for host-init.sh deploy-user (self-hosted OpenStack)
```

On a self-hosted OpenStack, the public key is used by `host-init.sh deploy-user` to authorize the deployment user on the OpenStack host. The filename must match `SSH_KEY_NAME` in your `.env` (default: `id_ed25519`).

> **Note on `.openrc`**: If you use an `.openrc` file generated by the OpenStack Dashboard, you **must remove the interactive password prompt** (`read -sr OS_PASSWORD_INPUT`) and set `export OS_PASSWORD=your-actual-password-here` directly.

### 3. Start Docker Compose and enter the container
If you want to start the container first and then open a shell inside it, use:
```bash
docker compose up -d
docker compose exec cave bash
```
If the container is not running yet, you can also open a shell directly with:
```bash
docker compose run --rm cave bash
```

### 4. OpenStack Initialization
The setup depends on what kind of OpenStack you use.

**Any OpenStack (including managed ones), in the container**: create the VM flavors. This only needs API access (admin rights for public flavors; without them, missing flavors are reported as warnings):
```bash
docker compose run --rm cave /cave/init-flavors.sh
```
(Or choose "Create VM Flavors" in the menu.)

**Self-hosted OpenStack (MicroStack, Sunbeam, DevStack, ...), on the OpenStack host, not in the container**: additionally run the host-level setup from a checkout of this repo (requires root). Run `./scripts/host-init.sh` without arguments for the full description. Verified on MicroStack only; check for each step whether your backend needs it:
```bash
sudo ./scripts/host-init.sh network       # NAT/forwarding, if the host routes the external network
sudo ./scripts/host-init.sh deploy-user   # `vpnsetup` user, only needed for --access host (see step 9)
sudo ./scripts/host-init.sh all           # both
```

**Windows VMs and UEFI firmware, on the OpenStack host (only if a hypervisor brings its own firmware)**: if Windows VMs boot with a black screen because the hypervisor ships 2M OVMF firmware (seen with MicroStack), replace it with the host's 4M firmware. This is a separate, generic tool in [scripts/ovmf/](scripts/ovmf/README.md):
```bash
sudo ./scripts/ovmf/ovmf-snap.sh microstack      # snap-based hypervisors
sudo ./scripts/ovmf/ovmf-apply.sh DIR            # any other layout, by hand
```

A managed OpenStack needs none of the host-level steps. See `.env.sample` (`OS_*` variables) and [docs/microstack-to-openstack-snap.md](docs/microstack-to-openstack-snap.md) for details.

### 5. Build Windows Base Images
If you need to generate Windows images for your CAVE Infrastructure deployment, refer to the [Windows Image Builder README](./windows-image-builder/README.md) for detailed instructions on preparing ISO files and building Windows images with QEMU.

### 6. Upload Windows Images to OpenStack
If you have generated Windows base images (from the Windows Image Builder), you need to upload them to OpenStack before building CAVE images:

```bash
docker compose run --rm cave /cave/upload-windows-image.sh
```

### 7. Pre-Build Setup
Before building CAVE base images, you need to set up the OpenStack environment and download required cloud images. This step:
- Creates and configures required security groups
- Downloads the Kali Linux cloud image
- Extracts and uploads it to OpenStack

Run the pre-build setup script:
```bash
docker compose run --rm cave /cave/pre-build-images.sh
```

### 8. Build CAVE Base Images
Before deploying, you must build the required base images and upload them to OpenStack using Packer. By default, this uses the official [CAVE Images repository](https://gitlab.opencode.de/BSI-Bund/cave/cave-images).

Start the interactive image builder:
```bash
docker compose run --rm cave /cave/build-images.sh
```

You can also specify a custom repository and a specific branch or commit hash:
```bash
# Example: Using a custom repo and the 'my-feature-branch' branch
docker compose run --rm cave /cave/build-images.sh https://git.example.com/custom-images.git my-feature-branch
```

The script also supports a quiet mode to reduce Packer output, showing only errors:
```bash
docker compose run --rm cave /cave/build-images.sh -q
```

During the interactive image selection, you can build multiple images at once by entering space-separated numbers, for example:
```text
1 3 5
```
This will build image 1, image 3 and image 5 in sequence. Use `A` to build all images or `Q` to quit.

The scripts automatically create required OpenStack flavors (like `client-medium`, `server-small`, `server-large`, `server-windows`) during the `init-flavors.sh` step, which match the requirements of the packer templates.

Follow the interactive prompts to build the necessary images. Wait until the builds finish successfully.

### 9. Deploy Infrastructure using the Wrapper
Now you can deploy the CAVE infrastructure using the interactive deployment wrapper.

Start the wrapper interactively:
```bash
docker compose run --rm cave /cave/deploy-wrapper.sh
```

The wrapper will:
- Validate your credentials and SSH key
- Let you choose an available configuration file (`/backend/configs/`)
- Automatically detect the associated user configuration file
- Support deploying with WireGuard or OpenVPN

Alternatively, you can skip the interactive menu and deploy directly:
```bash
# Deploy with OpenVPN
docker compose run --rm cave /cave/deploy-wrapper.sh day1

# Deploy with WireGuard and a custom prefix
docker compose run --rm cave /cave/deploy-wrapper.sh day1 --wg --lab-prefix my-training

# Managed OpenStack (no access to an OpenStack host): reach the VPN gateway directly
docker compose run --rm cave /cave/deploy-wrapper.sh day1 --access direct
```

The access mode can also be set permanently with `CAVE_ACCESS_MODE=direct` in `.env`. The default (`host`) reaches the VPN gateway through the OpenStack host and therefore needs the host-level setup from step 4 (`deploy-user`).

### 10. Destroy Infrastructure
Tear a deployment down again (in the container, like the deployment):
```bash
docker compose run --rm cave /cave/exterminate-wrapper.sh day1
# if `tofu destroy` fails and leaves resources behind, use the OpenStack CLI directly:
docker compose run --rm cave /cave/exterminate-wrapper.sh day1 --hard
```
The access mode must match the deployment: with `CAVE_ACCESS_MODE=direct` (or `--access direct`) no OpenStack host is contacted and no iptables cleanup happens. In host mode the wrapper cleans up the VPN forwarding rules on the OpenStack host (needs `SSH_KEY_NAME`). `--hard` works on the project of your current OpenStack credentials.

## Troubleshooting

### ❌ OVN Metadata Agent failing on newer kernels (MicroStack)

**Problem**: On newer kernels, the MicroStack OVN metadata agent may fail to start, causing VM networking issues (VMs cannot reach the metadata service or internet).

**Solution**: Run the provided fix script **on the OpenStack host** (not in the container):
```bash
sudo ./scripts/fix_ovn_metadata.sh
```

This script applies a sustainable patch to the OVN metadata agent service, making it compatible with newer kernel versions.

It is **MicroStack only**: it patches the `microstack` snap. It does nothing for other backends. Whether the `openstack-hypervisor` snap (Sunbeam) has the same problem is untested.

### ❌ "Please enter your OpenStack Password..." prompt appears

**Problem**: Your `.openrc` file contains the interactive password prompt.

**Solution**: Edit `.openrc` and replace the interactive `read -sr` lines with:
```bash
export OS_PASSWORD=your-actual-password-here
```

### ❌ "OS_PASSWORD is not set" error

**Problem**: Both `.env` and `.openrc` are missing the password.

**Solution**: 
Ensure `.env` has `OS_PASSWORD=your-password` or `.openrc` has `export OS_PASSWORD=your-password`.

## Manually Push to GitHub Container Registry

```bash
# Build locally (with BuildKit for better caching)
DOCKER_BUILDKIT=1 docker compose build

# Tag and push a version
docker tag ghcr.io/felixhertweck/cave-infrastructure-docker:latest ghcr.io/felixhertweck/cave-infrastructure-docker:v1.0.0
docker push ghcr.io/felixhertweck/cave-infrastructure-docker:v1.0.0
```
